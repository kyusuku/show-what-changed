# Docker export and explicit load

Status is a reviewed controlled prototype. The main implementation is unchanged. Real exporter parity and installed interruption checks remain required before promotion or gate acceptance.

The current combined Buildx build and load request can leave uncertain Engine image creation after cancellation during a Dockerfile build. A missing image immediately after abort does not prove that the daemon cannot finish a late load. The selected prototype separates completed local export from explicit Engine load. It records image creation intent immediately before the load request and preserves uncertainty after an issued request.

The archive lives in an owned private directory outside source snapshots and temporary application workspaces. The exporter receives a relative ASCII destination so spaces and commas in ancestor paths do not change exporter option parsing. Metadata and image IDs have bounded reads. The trusted Buildx exporter supplies the archive; the fixed trailer check does not claim complete tar validation. Export adds temporary disk requirements without imposing a new application image-size limit.

Independent review reproduced two initial defects. Disposal could outlive the shared cleanup deadline, and an exception from disposal could replace the original build error. The repair gives archive waiters the earlier of their local disposal deadline and any active run cleanup deadline. A normal successful build does not start the entire run's cleanup budget. Registry cleanup observes the same failed disposal promise, so the terminal result preserves the first operation error and also records cleanup failures. Cancellation keeps its existing precedence.

The repaired prototype passed 139 controlled tests with three real-Buildx cases explicitly skipped. Independent focused checks passed 17 existing tests and four new tests. They exercised the actual archive owner and runner terminal path with mocked Docker operations. They are not real Docker cleanup evidence.

One independent test showed that filesystem removal already issued after inactivity and identity checks can finish after its bounded wait expires. The result and saved manifest remain failed, and ownership and the lock remain retained. The reviewed copy now states that limit instead of promising that every timed-out archive remains intact. Its terminal suite passed seven tests, including the adopted late-removal regression. No code change was needed for that correction.

Directory creation rejects existing paths, unexpected initial contents, symlinks, and detectable identity changes. These checks assume trusted same-user setup code. They cannot distinguish an empty replacement between creation and first identity capture, or make a pathname check and later operating-system operation atomic. The documentation records those limits.

Promotion requires one actual pinned Buildx export with no Engine image creation, matching archive configuration digest, metadata digest, image ID and labels, and matching identity after explicit load. Exact cleanup must preserve separate sentinel resources and shared base images. The final installed package then needs the mandatory build/create interruption cells and targeted uncertain-load recovery checks. No result here accepts G07 or G15.

## Actual exporter observations

The first corrected real export command rejected attached provenance attestations because the Docker archive exporter cannot represent their manifest list. The next isolated trial disabled image attestations while retaining maximum private build metadata and all provenance requirements. Docker documents these controls separately in its [Buildx reference](https://docs.docker.com/reference/cli/docker/buildx/build/).

That real export completed. The Engine image inventory stayed identical and its bounded image-event query was empty. The 1,911,296-byte archive contains the intended sole Docker tag; its configuration digest matches the iid and metadata configuration digest. The metadata retains the pinned BusyBox material. The verifier rejected the normal tag-only OCI reference annotation before loading, so the trial remains failed. Its exact archive and separately owned sentinel container/network are retained, with the dedicated VM stopped. [development-docker-export.json](development-docker-export.json) records this partial evidence. A separate bounded load and recovery continuation must validate the same bytes, preserve the original failure, and close retained ownership. Product promotion remains held.

The retained archive subsequently loaded into the isolated Engine. Its Engine image ID equals its verified OCI manifest digest and descriptor, while its config digest still equals the iid and metadata config digest. Exact tag, tool labels, root filesystem layers, and platform match. The config-ID-only normal attempt remains failed. A separate manifest-backed recovery removed only that positively verified image and the original sentinels, preserved background resources, and proved VM shutdown. Runtime compatibility adaptation and complete installed-package parity remain pending.
